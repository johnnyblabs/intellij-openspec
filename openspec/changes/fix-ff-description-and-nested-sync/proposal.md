# Proposal

## Why

The pre-release workflow parity audit found two defects in workflows the plugin runs itself. Both produce wrong results without an error, so they're fixed before the next release rather than after it.

- **Fast-Forward ignores the request.** The workflow panel's Fast-Forward form asks "Describe what you want to build", but the description is used only to name the change. Generation then sees only the change name, so the proposal (and everything built on it) is written from a few words of kebab-case. Upstream's `ff` workflow builds every artifact "using context from the user's request".
- **Sync Specs misses nested capabilities.** OpenSpec supports capabilities in nested folders, such as `specs/identity/user-auth/spec.md`, and its archive syncs them (verified against the real CLI 1.15.0: the delta is keyed `identity/user-auth` and merged into `openspec/specs/identity/user-auth/spec.md`). The plugin's built-in Sync Specs reads only `specs/<name>/spec.md`, one level deep. A change whose deltas are all nested reports "No delta specs found"; a mixed change syncs only part of itself; and the workflow panel skips its "sync specs first?" archive prompt because it thinks the change has no deltas. Validation and Explore already handle nested capabilities; Sync is the last place that doesn't.

Tracked in the linked tracker entry.

## What Changes

- Fast-Forward carries the user's description into generation as the request the change is for. Over Direct API, every artifact generated by that Fast-Forward run gets it; for clipboard and editor-tab delivery, the prompt for the first artifact gets it. The description is not written to disk, matching upstream `ff`, which keeps the request in conversation context and runs `openspec new change "<name>"` without `--description`.
- Built-in Sync Specs finds delta specs at any depth under a change's `specs/` folder, keys each by its path relative to `specs/` (for example `identity/user-auth`), and merges it into the main spec at the same relative path, creating it with the full path in its title as OpenSpec does. The panel's archive prompt and the Sync Specs button see nested deltas too.
- Internal wording that calls Sync Specs a "view/diff utility" is corrected: it writes main specs.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `ff-panel`: Fast-Forward generation uses the user's description as the request for the change, not only to derive its name.
- `spec-sync`: delta specs are read at any depth under the change's `specs/` folder and merged into the main spec at the same relative path.

## Impact

- `toolwindow/WorkflowActionPanel` (Fast-Forward submit and the generation it triggers), `model/ArtifactInstruction` (a request section in the prompt), `services/ArtifactOrchestrationService.generateAllRemaining` (carries the request for one run).
- `services/SpecSyncService` (recursive delta discovery); `hasDeltaSpecs` and `getCapabilities` follow from it.
- Test-only: the parity contract test's reason text for `sync`; the comment on `OpenSpecSyncAction`.
- No new IntelliJ Platform APIs; the 2024.2+ floor is unaffected. No CLI-version gate: nested capabilities are read from disk.
