# OpenSpec CLI 1.16 — Feature Delta & Plugin Impact (vs 1.15)

> Every upstream claim below is cited to the [OpenSpec 1.16.0 changelog](https://github.com/Fission-AI/OpenSpec/blob/v1.16.0/CHANGELOG.md) and checked against the captured CLI output under `../../src/test/resources/fixtures/cli/1.16.0/`. 1.16.1 is out too; its changes are not covered here.

## 1. Summary

1.15 → 1.16 is a **small, mostly validation-side** release. No command, flag, workflow, AI-tool entry or JSON shape the plugin reads changed. The changes that matter to the plugin are three validation fixes (a broken `config.yaml` now fails `validate`, a single-line backtick span is no longer a code fence, and a `###Requirement:` header with no space is recognized), a new strict-only scenario-step warning, and a new install route with a higher npm Node.js floor. The plugin follows all of them. Two parity gaps remain, both listed in §4.

## 3. Per-feature detail

### 3.1 Node.js floor and install routes (#2159, #2160)
**Mechanics.** The npm package now requires Node.js 22.12.0 (Node 20 is end-of-life). The standalone binary does not use Node and is the default install since 1.15. The official installer moved to `openspec.dev/cli/`.
**Plugin assessment.** Supported. `CliInstallHints` shows the new commands and the new floor, and the upstream Quick Start is captured at 1.16.0 (`fixtures/upstream/readme-quick-start-1.16.0.md`) so a future change fails the hint test rather than going stale.
**Consumer how-to.** Install the standalone binary (no Node.js needed), or use npm on Node.js 22.12 or newer.

### 3.2 Scenario steps (#2079)
**Mechanics.** A `Scenario:` lacking a WHEN/GIVEN step or a THEN step is a warning in change deltas and main specs. Plain `validate` and `archive` are unchanged; `--strict` fails.
**Plugin assessment.** The CLI's verdict carries it, so default and strict results in the Validate action match the CLI when the CLI runs. The built-in fallback has no scenario-step check, so it is laxer than the client here, never stricter. Mirroring the check is deferred to a later release.
**Consumer how-to.** Each scenario needs a WHEN (or GIVEN) line and a THEN line. Use `--strict` to make the warning fail a run.

### 3.3 Broken `config.yaml` (#2127)
**Mechanics.** An unreadable or unparseable `openspec/config.yaml` makes `validate` exit 1 with an item-less error response (`unparseable_config` or `unreadable_config`). Other commands still warn and carry on.
**Plugin assessment.** Fixed in v0.16.0. Validate reports one error at `config.yaml` with the CLI's message and fix, and the Change Deltas pane shows the same error. Without the CLI, the built-in check shows a warning, because CLI 1.3–1.15 accept such a file.
**Consumer how-to.** Fix the YAML in `openspec/config.yaml`. Validate now reports it as a failure.

### 3.4 Inline backtick code (#2131)
**Mechanics.** A line that begins with triple-backtick inline code (```` ```npm test``` ````) is not a fence opener. Before this, it hid every requirement after it.
**Plugin assessment.** Fixed in v0.16.0. All four fence maskers share the `CodeFences` rule, which follows the CommonMark info-string rule. The regression fixture is the 1.16.0 corpus spec `inline-backtick-req`.
**Consumer how-to.** Nothing to change. Inline code in a requirement no longer hides the requirements after it.

### 3.5 `###Requirement:` with no space (#2133)
**Mechanics.** `validate` now reports duplicate or misplaced main-spec requirements written with no space after the hashes, as archive already reads them. The CLI does recognize the header in main specs. Its scenario attachment is unreliable for those headers, so a requirement written this way is often reported as "must have at least one scenario".
**Plugin assessment.** Partly fixed. In change deltas (ADDED, MODIFIED, REMOVED, RENAMED), the built-in validator and the delta inspection recognize the header, and archive already did. In main specs, the plugin still ignores it, so it doesn't report the duplicate or misplaced-requirement error the CLI gives. Both forms reject the spec, so the verdict agrees, but the message differs. See §4.
**Consumer how-to.** Write `### Requirement:` with the space, in main specs and in change deltas. The unspaced form is not a supported style.

### 3.6 Error response naming a store (#2077)
**Mechanics.** When no OpenSpec root is found and stores are registered, the error names the store whose id matches the repo name. It only suggests the store and never picks one.
**Plugin assessment.** Supported as an error response. The plugin treats it as a failed run and doesn't parse the suggestion text.
**Consumer how-to.** Follow the suggested `--store` flag from the terminal. The plugin doesn't pick stores.

### 3.7 Shell completion (#2172)
**Mechanics.** `openspec completion install zsh` now honors an absolute `ZDOTDIR`.
**Plugin assessment.** Not applicable. The plugin doesn't install shell completion.

## 4. Gaps and deferred work

- **Scenario-step check in the built-in fallback (§3.2).** Deferred. It is a strict-only warning, so the fallback stays laxer than the CLI, not stricter.
- **Duplicate and misplaced unspaced main-spec requirements (§3.5).** Not mirrored. The plugin's main-spec rule still needs the space, so these headers get the requirement-presence error where the CLI gives a duplicate or misplaced error. Both verdicts reject the spec.
- **1.16.1.** A patch release changes heading closing sequences (`## Purpose ##`), reports requirements under unrecognized delta headers as errors, and masks HTML comments when looking for orphaned requirements. Those changes are not part of this analysis.

## 5. Verification

- The 1.16.0 fixture set is the verdict source (`../../src/test/resources/fixtures/cli/1.16.0/`), including the corpus spec for §3.4 and the broken-config captures for §3.3.
- `CliInstallHintsTest` checks the install commands word for word against `readme-quick-start-1.16.0.md`.
- The §3.5 delta behaviour was checked against the CLI by hand: a delta with the unspaced header and a scenario is valid, and the same delta without a scenario is reported as missing a scenario. The main-spec behaviour was checked the same way.
